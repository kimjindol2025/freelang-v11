# FreeLang 9절 코딩규칙 (2026-05-14)

## 왜 규칙이 필요한가

모든 실수는 공통된 뿌리에서 시작된다.  
**리서치 없이 구현에 진입하면 기존 가이드를 놓치고, 나중에 기초부터 다시 점검해야 하는 더 큰 비용이 발생한다.**

FreeLang 프로젝트를 진행하면서 이 패턴이 반복되었다:
- table-tennis-club 세션: CLUB-APP-BASE-GUIDE.md 핵심 지침 놓침
- 5개 앱 분석: 공통 실수 패턴 확인
- 2026-05-14: 9절 코딩규칙 공식 확정

**핵심 인사이트**: 빨리 결과물을 만들고 싶은 성급함이 리서치를 생략하게 만든다.  
**해결책**: 의식적으로 늦춘다. 이것이 9절 코딩규칙의 정신이다.

---

## 핵심 원칙: 순서는 법이다

작업 순서는 다음과 같이 고정된다.

```
리서치 → 플랜모드 → 문서화(PLAN.md) → 태스크 등록 → 구현 → 검증
```

**금지 사항**: "응 진행해" 같은 승인을 받아도 곧바로 구현에 들어가는 것은 금지다.  
**필수 사항**: 새 작업 시작 전 반드시 다음을 먼저 마친다:
1. CLAUDE.md 전체 읽기
2. 관련 가이드 파일 확인
3. tasks.dclub.kr 프로젝트 확인
4. 태스크 등록

## 9절 전체 규칙

### 1절 — 작업 순서
**원칙**: 리서치 → 플랜모드 → 문서화 → 태스크 등록 → 구현 → 검증  
**규칙**: 순서를 건너뛰지 않는다. 문서화는 구현 전 무조건 완료해야 한다.

**체크리스트**:
- [ ] CLAUDE.md 읽음
- [ ] 관련 파일 검토 (MISTAKES-100, ARCHITECTURE 등)
- [ ] PLAN.md 작성 (1-2페이지 outline)
- [ ] tasks.dclub.kr에 태스크 등록
- [ ] 구현 시작

### 2절 — 협의 원칙
**금지 사항**: 혼자 결정하는 것  
**필수 사항**: 반드시 협의한다.

대상:
- 아키텍처 변경
- Stage 설계
- 인터페이스 변경 (함수 시그니처, API 구조)
- 새 모듈/파일 추가
- 기존 로직 리팩터링

### 3절 — Stage 규칙
**원칙**: Stage 하나에 기능 하나만  
**규칙**:
- 중간 단계 실패 시 해당 Stage 처음부터 재시작
- 검증은 실제 명령 실행으로만 (눈으로 보고 통과 선언 금지)

**예시 (실패 케이스)**:
```
Stage 1: 함수 추가 (50줄)
Stage 2: 테스트 (30개) — 실패
→ Stage 2만 재시작 (Stage 1은 유효)

중간 실패:
Stage 3: 통합 테스트 중 버그 발견
→ Stage 3 처음부터 재시작 (Stage 1-2는 유효)
```

### 4절 — 코드 품질
**규칙**:
- 빌드·타입 체크 경고 0
- 경고가 있으면 다음 단계 진행 불가
- 핵심 파일 줄 수 제한은 스택별로 사전 협의
- 추가보다 줄이는 방향 기본
- WHY 주석만 허용 (WHAT 주석은 금지)

**검증 명령어**:
```bash
npm run build      # 빌드 경고 확인
npx tsc --noEmit  # 타입 체크
npm run test:fast # 테스트
```

### 5절 — 파일 수정
**규칙**: Edit 도구 사용. sed -i 금지.

**이유**: Edit은 변경 사항 추적 가능, sed는 검증 불가능

### 6절 — 의존성
**원칙**: 내장 모듈과 기존 코드로 해결 우선  
**규칙**:
- 새 외부 패키지 추가 시 협의 필수
- 추가 시 이유 문서화 필수 (DEPENDENCIES.md)

**현재 FreeLang 의존성**:
```json
"dependencies": {}  // npm 패키지 0개 (Node.js 내장만 사용)
```

### 7절 — 롤백
**금지 사항**: 문제 발생 시 핫픽스  
**규칙**:
- 원인 파악 후 해당 Stage 처음부터 재시작
- --force, --no-verify 절대 금지
- 커밋 히스토리 보존 (amend 금지, 새 커밋만)

**예시**:
```
버그 발견 → 핫픽스 금지
→ 원인 분석 (왜 실패했나?)
→ Stage 처음부터 재시작
→ 완료 후 검증
```

### 8절 — 완료 처리
**규칙**: 검증 완료 후 다음 3가지 모두 완료해야 Stage 완료

1. **git commit** (의미 있는 메시지)
2. **Gogs push** (--force 금지)
3. **블로그 포스팅** (500자 이상, 마크다운)

**금지**: 검증 전 push 절대 금지

### 9절 — 태스크 로그
**규칙**: 구현 중 단계별 진행 상황을 tasks.dclub.kr에 로그 기록  
**타이밍**: 태스크 등록은 구현 시작 전

**로그 내용**:
- Stage 1 시작: "N절 규칙 검토 중"
- Stage 1 완료: "N절 구현 완료, M개 함수 추가"
- 실패: "N절 테스트 실패, 원인: X"

  2. 기존 UI 패턴 무시
  3. 아키텍처 협의 없음

### 결론
**느린 것처럼 보이지만 빠르다.**  
- 리서치 + 문서화 (5시간)
- 구현 + 검증 (2시간)
- 총 7시간, 실수 최소

vs

- 구현 먼저 (2시간)
- 버그 수정 (4시간)
- 리팩터링 (3시간)
- 총 9시간 이상, 기술부채 증가

Day 2: 구현 + Stage 1 검증

### ❌ 잘못된 순서
```
Day 1: "응 진행해" → 바로 구현 시작
Day 2-3: 버그 수정
Day 4: 기초 다시 점검

```

## 규칙 위반 시

| 위반 | 결과 |
|------|------|
| 순서 건너뛰기 | 해당 Stage 재시작 |
| 협의 없이 결정 | 아키텍처 리뷰 필수 |
| 경고 무시 | 빌드 실패, 다음 진행 불가 |
| 검증 전 push | 롤백 + Stage 재시작 |
| 블로그 없음 | Stage 미완료 |

## 이 규칙을 따르는 이유

1. **실수 최소화**: 공통 패턴 제거
2. **속도 향상**: 느려 보이지만 총 시간 단축
3. **품질 보증**: 빌드 경고 0 = 신뢰도 높음
4. **추적 가능**: 태스크 + 커밋 + 블로그로 완전 기록
5. **재현 불가능한 버그 방지**: 문서화로 원인 파악 용이
