## 왜 규칙이 필요한가

모든 실수는 공통된 뿌리에서 시작된다.  
**리서치 없이 구현에 진입하면 기존 가이드를 놓치고, 나중에 기초부터 다시 점검해야 하는 더 큰 비용이 발생한다.**

FreeLang 프로젝트를 진행하면서 이 패턴이 반복되었고, 11개 절로 정규화했다.

---

## 핵심 원칙: 순서는 법이다

작업 순서는 다음과 같이 고정된다.

```
리서치 → 플랜모드 → 문서화(PLAN.md) → 태스크 등록 → 구현 → 검증
```

**금지 사항**: "응 진행해" 같은 승인을 받아도 곧바로 구현에 들어가는 것은 금지다.  
**필수 사항**: 새 작업 시작 전 반드시 다음을 먼저 마친다:
1. CLAUDE.md 전체 읽기
2. 관련 가이드 파일 확인
3. tasks.dclub.kr 프로젝트 확인
4. 태스크 등록

## 11절 전체 규칙

### 1절 — 작업 순서
**원칙**: 리서치 → 플랜모드 → 문서화 → 태스크 등록 → 구현 → 검증  
**규칙**: 순서를 건너뛰지 않는다. 문서화는 구현 전 무조건 완료해야 한다.

**체크리스트**:
- [ ] CLAUDE.md 읽음
- [ ] 관련 파일 검토 (MISTAKES-100, ARCHITECTURE 등)
- [ ] PLAN.md 작성 (1-2페이지 outline)
- [ ] tasks.dclub.kr에 태스크 등록
- [ ] 구현 시작

### 2절 — 협의 원칙
**금지 사항**: 혼자 결정하는 것  
**필수 사항**: 반드시 협의한다.

대상:
- 아키텍처 변경
- Stage 설계
- 인터페이스 변경 (함수 시그니처, API 구조)
- 새 모듈/파일 추가
- 기존 로직 리팩터링

### 3절 — Stage 규칙
**원칙**: Stage 하나에 기능 하나만  
**규칙**:
- 중간 단계 실패 시 해당 Stage 처음부터 재시작
- **검증은 실제 명령 실행으로만** (눈으로 보고 통과 선언 금지)

**예시 (실패 케이스)**:
```
Stage 1: 함수 추가 (50줄)
Stage 2: 테스트 (30개) — 실패
→ Stage 2만 재시작 (Stage 1은 유효)

중간 실패:
Stage 3: 통합 테스트 중 버그 발견
→ Stage 3 처음부터 재시작 (Stage 1-2는 유효)
```

### 4절 — 코드 품질 (2026-05-15 수정)
**규칙**:
- 빌드·타입 체크 경고 0
- 경고가 있으면 다음 단계 진행 불가
- **핵심 파일 300줄 이하 (기본값)** — 초과 시 분리 협의 필수
- 추가보다 줄이는 방향 기본
- WHY 주석만 허용 (WHAT 주석은 금지)

**검증 명령어**:
```bash
npm run build      # 빌드 경고 확인
npx tsc --noEmit  # 타입 체크
npm run test:fast # 테스트
```

**핵심 파일 기본값**:
| 파일 | 기본값 | 이유 |
|------|--------|------|
| stdlib-*.ts | 300줄 | 단일 책임 원칙 |
| interpreter.ts | 400줄 | 복잡도 상승 주의 |
| eval-*.ts | 300줄 | 인지 부하 감소 |
| test-*.ts | 제한 없음 | 테스트 규모 무관 |

초과 시: 분리 협의 필수 (e.g., stdlib-collection.ts → stdlib-collection-*.ts 분할)

### 5절 — 파일 수정
**규칙**: Edit 도구 사용. sed -i 금지.

**이유**: Edit은 변경 사항 추적 가능, sed는 검증 불가능

### 6절 — 의존성
**원칙**: 내장 모듈과 기존 코드로 해결 우선  
**규칙**:
- 새 외부 패키지 추가 시 협의 필수
- 추가 시 이유 문서화 필수 (DEPENDENCIES.md)

**현재 FreeLang 의존성**:
```json
"dependencies": {}  // npm 패키지 0개 (Node.js 내장만 사용)
```

### 7절 — 롤백
**금지 사항**: 문제 발생 시 핫픽스  
**규칙**:
- 원인 파악 후 해당 Stage 처음부터 재시작
- --force, --no-verify 절대 금지
- 커밋 히스토리 보존 (amend 금지, 새 커밋만)

**예시**:
```
버그 발견 → 핫픽스 금지
→ 원인 분석 (왜 실패했나?)
→ Stage 처음부터 재시작
→ 완료 후 검증
```

### 8절 — 완료 처리
**규칙**: 검증 완료 후 다음 3가지 모두 완료해야 Stage 완료

1. **git commit** (의미 있는 메시지)
2. **Gogs push** (--force 금지)
3. **블로그 포스팅** (500자 이상, 마크다운)

**금지**: 검증 전 push 절대 금지

### 9절 — 태스크 로그
**규칙**: 구현 중 단계별 진행 상황을 tasks.dclub.kr에 로그 기록  
**타이밍**: 태스크 등록은 구현 시작 전

**로그 내용**:
- Stage 1 시작: "N절 규칙 검토 중"
- Stage 1 완료: "N절 구현 완료, M개 함수 추가"
- 실패: "N절 테스트 실패, 원인: X"

### 10절 — 보안 체크 (2026-05-15 신설) ⭐

**원칙**: 보안은 사후 대응이 아니라 사전 체크  
**금지 사항**: 코드 파일, 메모리 파일, 주석에 평문 저장

**체크리스트**:

#### API 키 / 토큰 / 비밀번호
- [ ] 환경변수(.env)로만 관리
- [ ] 코드에 평문 저장 금지
- [ ] 메모리 파일에 저장 금지
- [ ] 주석에 작성 금지
- [ ] git history에 노출 금지 (pre-commit hook 필수)

#### 엔드포인트 보안
- [ ] 새 엔드포인트: 인증 여부 명시 (공개/인증/관리자)
- [ ] DB 쿼리: SQL Injection 방어 (parameterized query 필수)
- [ ] 요청 본문: XSS/CSRF 방어 (html-escape, auth-csrf-token)

#### 데이터 민감도
- [ ] 비밀번호: bcrypt 해시 (평문 저장 금지)
- [ ] 세션: HttpOnly + Secure + SameSite (server-set-cookie)
- [ ] API 응답: 불필요한 정보 노출 금지 (obj-omit 사용)

**위반 시**:
- 환경변수 누락: 해당 커밋 push 불가 (pre-commit hook 거절)
- 평문 저장 발견: 즉시 롤백 + Stage 재시작
- 검증 전 push: 강제 롤백 + 재협의

**현재 보안 상태**:
- ✅ Gogs 토큰: 환경변수 저장 (.claude/GOGS_TOKEN.env)
- ❌ 블로그 API Key: 메모리 파일 평문 저장 → **개선 필요**

### 11절 — 롤백 기준 (2026-05-15 신설) ⭐

**원칙**: 성급한 반복 시도는 기술부채 증가  
**규칙**:
- **검증 실패 2회 이상** → 즉시 롤백
- **3회째 시도** → 반드시 협의 후 진행
- **혼자 계속 시도 금지** (원인 분석 필수)

**롤백 판단 기준**:

| 상황 | 조치 |
|------|------|
| 검증 실패 1회 | 버그 수정, Stage 재시작 |
| 검증 실패 2회 | **즉시 롤백 (git reset --hard)** |
| 롤백 후 재시도 결정 | 협의 필수 (원인 분석 + 아키텍처 검토) |
| 3회 이상 실패 | 구조적 문제 → 해당 Stage 전면 재설계 |

**예시**:
```
Stage 2 검증 실패 1회
→ 버그 수정, 재검증
→ 실패 2회
→ git reset --hard (Stage 1로 복귀)
→ 협의 (무엇이 잘못됐는가?)
→ Stage 2 재설계 후 재시작
```

**롤백 방법**:
```bash
# 마지막 유효한 커밋 찾기
git log --oneline | head -10

# 롤백 (해당 커밋으로 복귀)
git reset --hard <commit-hash>

# 작업 디렉토리 정리
npm run build
npm run test:fast
```
