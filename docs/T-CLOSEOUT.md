### 판정과 시간 해석

Jest 기록상 전체는 **1,432개 통과 / 0개 실패 / 0개 건너뜀 / 0개 todo**다. 그러나 6번의 시간은 **1ms**다. 사용자의 “하나라도 시간이 0에 가까우면 미확정” 기준을 적용하여 **실패 0개 최종 확정 및 T 작업 종료는 보류**한다. `passed` 기록을 실패로 바꾸거나, 1ms를 건너뜀으로 바꾸어 보고하지 않는다.

2~6번과 8~10번의 테스트 시간은 모두 존재한다. 검증 HEAD의 테스트 소스를 읽으면 2~5번 및 8~10번은 동기식 자식 프로세스로 컴파일을 호출하므로 아래 시간은 그 호출을 포함한 테스트 전체 경과 시간이다. **컴파일 프로세스만의 별도 실측 시간은 확인 불가**다. 해당 로그에는 항목별 컴파일 시작·종료 시각이나 별도 컴파일 시간 출력이 없으며, 자식 프로세스 출력은 코드에서 pipe로 받는다. 특히 6번은 새 컴파일을 수행하지 않고 앞선 단계에서 생성한 세 파일의 SHA를 비교하므로 1ms를 자기 컴파일 시간이라고 해석할 수 없다. 샤드 2 로그에는 자기 컴파일 테스트 스위트 전체 `51.089 s`가 기록되어 있지만 이를 개별 컴파일 시간으로 대체하지 않는다.

### 로컬과 GitHub의 차이 하나

실행 조건 차이: 로컬 전체 검사 기록은 coverage 75% 기준에 실제 값 25.73%로 미달했지만, GitHub의 `test:ci-jest`는 기존 CI 설정에서 coverage 수집과 임계값 검사를 비활성화한다. 로컬 로그의 명령·임계값 실패와 GitHub 로그의 명령·검증 HEAD의 설정으로 확인했다. 이것은 coverage 판정 차이 하나의 근거이며, 별도의 로컬 네이티브 테스트 2개 실패 원인까지 설명한다고 주장하지 않는다.
