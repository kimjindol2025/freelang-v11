# D-3 연결 누수와 프로세스 제한 시험 보고서

기준 가지: `db-stability`, 시작 HEAD `9ffa9cd00bf3d98586fc92cfd61670ac9645beaf`. 무거운 시험은 임시 디렉터리와 공용 잠금 `flock -n -o /tmp/fl-heavy.lock`을 사용했다. 실행 위치: 메인. 23·25 서버에는 접속하지 않았다.

## 1. 연결 누수 원문

코드 수정 전에 경로 문자열을 `fl_db_exec`에 전달해 호출마다 소유 연결을 열었다. 매개변수 오류, 저장점 시작 오류, 저장점 해제 오류를 각각 1000회 일으켰다. 저장점 오류 두 종류는 시험 전용 링커 래퍼로 해당 `sqlite3_exec` 호출에만 실패를 주입했다. 다른 SQL은 그대로 SQLite에 전달했다. 원문:

```text
DB_LEAK_BEFORE_RC=1
DB_LEAK_PATH=params DB_LEAK_FD_BEFORE=4 DB_LEAK_FD_AFTER=2004 ERRORS=1000 WRAPPED_FAILURES=0
DB_LEAK_PATH=savepoint DB_LEAK_FD_BEFORE=4 DB_LEAK_FD_AFTER=2004 ERRORS=1000 WRAPPED_FAILURES=1000
DB_LEAK_PATH=release DB_LEAK_FD_BEFORE=4 DB_LEAK_FD_AFTER=2004 ERRORS=1000 WRAPPED_FAILURES=1000
```

같은 커밋된 시험을 수정 후 다시 실행한 원문:

```text
DB_LEAK_AFTER_RC=0
DB_LEAK_PATH=params DB_LEAK_FD_BEFORE=4 DB_LEAK_FD_AFTER=4 ERRORS=1000 WRAPPED_FAILURES=0
DB_LEAK_PATH=savepoint DB_LEAK_FD_BEFORE=4 DB_LEAK_FD_AFTER=4 ERRORS=1000 WRAPPED_FAILURES=1000
DB_LEAK_PATH=release DB_LEAK_FD_BEFORE=4 DB_LEAK_FD_AFTER=4 ERRORS=1000 WRAPPED_FAILURES=1000
```

## 3. 흔들림 원인 원문과 선택한 방법

D-2 대상 3회차의 원문은 `PARALLEL_USER_TASK_COUNT=3140`, `PARALLEL_ULIMIT_U=3145`, `FAILED_SLOTS=20 SUCCESSFUL_SLOTS=0`이었다. 같은 호스트의 100회 태스크 표본은 `MIN=3132 MAX=3144 SPAN=12`로, 시험 여유 5개보다 크게 변했다. 이는 원래 실패의 **추측** 근거다. D-2 실패 순간의 태스크 수를 직접 기록하지 않아 그 한 번의 인과 관계는 확정하지 않는다.

D-3에서는 같은 `run-parallel` 입력과 같은 판정식(`failed>0`, `succeeded>0`, 합계 20)을 사용했다. 별도 사용자 네임스페이스의 하위 UID로 실행해 메인 사용자 태스크 변동을 분리했다. 시험 실행 파일 안에서 태스크 수를 읽어 기존 `측정값 + 5` 제한을 설정했다. fork 직전과 실패 직후를 같은 실행 파일에서 계측했다. 원문:

```text
DB_FORK_MEASURED_TASKS=1 DB_FORK_SET_LIMIT=6
DB_FORK_PRE_TASKS=6 DB_FORK_LIMIT=6 DB_FORK_RESULT=fail DB_FORK_FAILURE_TASKS=6 DB_FORK_ERRNO=11
```

실패 시점에 사용자 태스크 수가 설정 제한 6개에 닿고 fork가 errno 11로 실패하는 기제는 확인됐다. 20회에서 이 값과 판정이 일정했다. 기존 `tests/run-task931.sh`의 기준 파일, 기대값, 제한 계산식은 변경하지 않았다. 메인의 전체 시험은 별도 사용자 격리가 아닌 기존 시험 그대로 실행한다.

## 6. http_server.c 손으로 맞출 목록

코1 가지 `v11-x86-seed-public`의 확인 시점 HEAD는 `d0153309e23a0738c20e6d9546b1263960f68bf2`였다. db-stability 가지는 `runtime/http_server.c`를 수정하지 않아 현재 두 가지 사이에 이 파일의 텍스트 충돌은 없다. 코1 작업이 먼저 끝난 뒤 다음 연결 지점을 수동 확인한다. 합치기는 하지 않았다.

- `runtime/http_server.c:215`, `:250`, `:265`: 지속 워커의 fork·재시작과 `runtime/db.c:87`의 PID별 DB 핸들 재열기가 함께 동작하는지 확인.
- `runtime/http_server.c:75`, `:114`, `:285`, `:328`: 공유 연결 수 복구·워커 재시작과 DB 30초 잠금 대기의 종료 순서 확인.
- `runtime/http_server.c:1144`, `:1152`, `:1217`: SIGCHLD 설정, 풀 중지·기존 워커 drain 경로에서 DB 연결과 WAL 정리가 완료되는지 확인.
