### 기준 가지와 변경 범위

원격에 `main` 가지는 없고 기본 가지는 `master`다. 이를 요청한 기본 가지로 해석하여 `9097aac3b8655b770fa126e2e3ad76c3850e502a`에서 `perf/t22-set-fix`를 만들었다. 이 기준 소스에는 식마다 Set 4개를 생성하는 코드가 존재한다. 다른 작업 가지에서 확인한 테스트 통과 결과를 이번 기준 코드의 결과로 사용하지 않는다.

측정 준비 커밋은 `791a11bb49283a30f4ad733bf0405d7693b54979`이며 새 `perf.yml` 파일 한 개만 포함한다. 워크플로는 수동 실행만 허용하고 Ubuntu 24.04, Node 24, 작업 제한 30분으로 구성했다. CI 안에서 bootstrap을 빌드한 뒤 자기 컴파일을 새 Node 프로세스로 3회 실행하도록 작성했다. 각 회차의 GNU time 경과 초, 최대 RSS(KiB), 생성 JS SHA-256과 CPU 모델·아키텍처·Node 버전을 결과물로 저장하도록 했다. 선택 입력으로 기존 Jest 설정의 전체 목록을 3개 샤드에서 실행할 수 있도록 구성했다. 아직 실행으로 검증된 워크플로는 아니다.

로컬에서 자기 컴파일·성능 측정·bootstrap 재생성을 수행하지 않았다. Set 변경은 기준값 측정 이후 단계이므로 아직 적용하지 않았다. 소스·테스트·기대값·기존 실행기·기존 CI 설정은 변경하지 않았다. 원격 저장소와 로그의 경로·소유자 정보는 `<가림>`이다.

### 실행 요청과 차단 근거

1. 측정 준비 커밋을 GitHub의 작업 가지에 푸시했다.
2. 해당 가지의 새 워크플로 파일을 GitHub Contents API로 조회하여 존재를 확인했다. 파일 blob SHA는 `5ad8149278b97bafe70714933378dbc0fd2cc241`이다.
3. GitHub의 등록된 워크플로 목록에는 기존 4개만 있고 새 측정 워크플로는 없었다.
4. `gh workflow run`의 가지 지정 요청은 HTTP 404였다.
5. 파일명을 지정한 REST dispatch 요청도 HTTP 404였다. 실행 ID가 발급되지 않았으며 측정 작업은 시작되지 않았다. 두 방식의 실패 후 같은 요청을 반복하지 않았다.

GitHub 공식 문서는 `workflow_dispatch`가 기본 가지에 파일이 있어야 실행된다고 명시한다. 출처: [GitHub 수동 워크플로 실행 조건](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_dispatch).

현재 요청은 기본 가지 병합과 기존 CI 변경을 금지한다. 따라서 새 워크플로를 기본 가지에 반영하거나 기존 워크플로를 측정용으로 바꾸는 조치는 수행하지 않았다. 재개에는 새 수동 워크플로의 기본 가지 등록이 선행되어야 하며, 현재 금지 조건에 대한 별도 결정이 필요하다.
