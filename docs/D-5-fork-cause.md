## 3. 원인 판정

지시서의 비교 기준에 따라 **컴퓨터 부하 탓**으로 판정한다. 메인에서 `10/50` 실패했고, 격리 UID에서는 `0/50` 실패했다. 메인 실패 14회차는 baseline 태스크 `3631`, 설정 제한 `3636`, 첫 fork 실패 직후 태스크 `3640`; 50회차는 baseline `3631`, 제한 `3636`, 첫 실패 직후 `3658`이다. 제한 계산 후 다른 과정의 태스크가 늘어나는 현상이 직접 관측됐다. 반면 일부 실패는 관측 태스크 수가 제한 아래이고 증가 과정도 없었으므로, 모든 실패의 개별 기제를 특정하지 않는다. DB 코드 변경을 원인으로 판정할 근거는 없고 DB 코드는 수정하지 않았다.

## 4. 고칠 방법 제안만

1. **격리 UID 실행을 기본으로 적용**: D-3 방식으로 fork 시험 구간을 별도 UID에서 실행한다. 기존 제한 `측정 태스크+5`와 성공·실패 판정을 그대로 유지할 수 있다. 이번 측정은 `50/50` 통과했다. 실행 환경에 사용자 네임스페이스가 필요하다.
2. **제한 여유와 fork 시도 수를 함께 조정**: 메인에서 관측한 baseline 대비 최대 증가 `27`을 넘는 여유를 주고, 성공·실패가 모두 발생하도록 시도 수를 함께 조정한다. 이는 시험 제한과 입력·기대값 변경이 필요하므로 사장님 승인 전에는 적용하지 않는다.

두 방법 모두 이번 커밋에는 적용하지 않았다.
