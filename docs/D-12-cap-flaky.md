stderr also contained `HTTP_WORKER_RESTART ... reason=request-limit detail=75` records during each failure snapshot. These records show worker rotation; they do not establish a separate cause. The pre-fix source in `runtime/http_server.c` was:

```c
if (http_rate_shared->active_connections >= http_max_conn) {
    struct pollfd listener = {.fd = server, .events = POLLIN};
    int ready = poll(&listener, 1, 50);
    if (ready > 0 && (listener.revents & POLLIN)) {
        int client = accept(server, NULL, NULL);
        if (client >= 0) {
            http_send_busy(client);
            close(client);
            http_pool_request_enter();
        }
    }
}
```

The pool manager checked `active_connections >= http_max_conn`, polled for up to 50 ms, accepted a connection, and sent 503 without checking capacity again. The failure snapshot plus the immediate follow-up 200 and this unchecked admission path identify a transient stale-capacity decision in the recovery window. No queue backlog or established TCP connections remained in the captured snapshot. This is the evidence-based root cause; no claim is made that the worker restart records caused it.

## 4. 변경 및 커밋 순서

재현 시험을 먼저 커밋한 뒤 런타임을 수정했다. 기대 출력과 CAP 조건은 바꾸지 않았다.

- `50a421e4bd34c855a831f29bae297849447996ed` — CAP 회복 반복 재현 시험.
- `90beada517944e689f225f9363a8aa02a1c6bf98` — 503 직후 후속 조회 진단.
- `1b482ef0` — 실패 순간 listen queue와 서버 로그 기록 추가.
- `70adba1b97bccbc56669f99bb43efbfdaa457301` — `runtime/http_server.c:142-160, 364-378`에서 accept 후 잠금 아래 용량을 다시 확보하고, 여유가 생긴 경우 해당 연결을 처리.

변경된 동작은 포화 전 검사와 accept 사이에 용량이 풀린 요청을 놓치지 않는 것이다. 용량이 여전히 찬 경우 기존 503 응답이 유지된다. 서버 측 대기나 재시도는 추가하지 않았다.
